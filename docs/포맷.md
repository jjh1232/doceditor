## 지금까지 확인된 것

**사람이 확인함 (2026-09-07).** 94곳을 채운 hwp 를 네이버 뷰어에서 열었다 —
원본과 나란히 놓고 차이가 없었고, `칸01`~`칸33` 이 전부 제자리였다.

이게 통과하면서 **마지막 미지수였던 `PARA_LINE_SEG` 문제가 풀렸다.**
글자 수를 바꾸면 파일에 저장된 줄 배치 좌표가 낡은 값이 되는데, **뷰어가 다시 계산한다.**
안 건드려도 된다.

**사람이 확인함 (2026-09-14).** 기능을 하나씩만 쓴 시험 파일 일곱 개를 만들어
네이버 웨일 뷰어로 전부 열었다. `make-trials.mjs` 가 만든다.

```
0 다시쓰기   내용은 그대로, 직렬화·압축·제자리 쓰기만 밟는다
1 글자       빈 칸 여덟 군데
2 사진       통에 스트림 새로 붙이기 + gso 3층      ← 이게 통과한 게 제일 크다
3 서식       11pt + 150%
4 크기만  5 줄간격만  6 전부
```

**통에 스트림을 새로 붙이는 길이 열렸다.** 빈 FAT 칸 찾기, 디렉터리 슬롯 쓰기,
슬롯이 없을 때 디렉터리 섹터 늘리기, 레드-블랙이 아닌 평범한 이진 트리로 끼우기 —
전부 실물 뷰어에서 통과했다. 제일 위험하다고 적어 둔 곳이 여기였다.

**서식도 통과했다.** DocInfo 에 CHAR_SHAPE·PARA_SHAPE 를 새로 만들고 ID_MAPPINGS 를
올리는 길이 맞았다.

**자동 검증.** 실제 채용 문서 10개(hwp 9 · hwpx 1)로 열기 → 고치기 → 저장 →
**저장한 걸 다시 열기** 까지 전부 통과. 세 경로를 다 밟는다:

```
빈 칸 채우기        PARA_TEXT / <hp:t> 를 새로 만들어 끼운다
글자 있는 칸 고치기  기존 것을 갈고, 서식 조각 목록을 정리한다
체크 상자           □ 를 ■ 로
```

아직 사람이 안 본 것: **hwpx 저장본**(`Downloads/동아고등학교_저장테스트.hwpx`),
그리고 hwp 의 **기간 칸·체크 상자**(3페이지쯤).

## 형식 탭 · 자동 판별 — 2026-09-15

한 페이지, 한 엔진에 **형식 탭**을 둔다. 지금 탭은 `HWP`(hwp·hwpx) 와 `一太郎`.

- **탭은 설명·안내만 바꾼다.** 여는 건 탭과 상관없이 `sniffFormat()` 이 파일 내용으로 가른다.
  탭을 잘못 골라 「안 열린다」 가 되면 안 된다. 一太郎 를 HWP 탭에 떨궈도 一太郎 탭으로 옮겨 준다.
- **탭마다 주소가 따로 있다.** 「一太郎 ファイル 開く」 검색이 그 탭으로 바로 들어와야 한다.
  프로토타입은 `#hwp` / `#jtd`, 배포 때는 `/form/<언어>/<형식>/` (아래 「prelaps 도구로 올릴 때」).
- 편집 화면에서는 탭을 숨긴다. 저장 버튼 문구와 **내려받는 확장자는 문서 형식을 따른다**
  (예전엔 hwpx 도 `_작성.hwp` 로 내려받아졌다).

```
zip (PK)                      → hwpx
CFB + FileHeader 스트림        → hwp
CFB + DocumentText 스트림      → jtd   ← hwp 와 같은 통이라 앞 바이트로는 못 가른다
```

### 一太郎 (.jtd) — 레코드 규칙과 채우기 (2026-09-16)

표본 4개(문부과학성 様式A-1·2·3·5)로 확정한 규칙. 엔진은 `openJtd` · `saveJtd` · `jtdFit`,
실측 도구는 `test/engine/probe-jtd*.mjs`, 검증은 `test/engine/test-jtd.mjs`.

```
DocumentText    압축 없음 · UTF-16BE 워드열
  0   "SsmgV.01"  u32 세그먼트 수 · u32 0x100 · u32 …
  10  "TextV.01"  u32 LEN        ← 있으면 본문은 16 부터 LEN 워드
                                 없는 파일(様式A-2)은 10 부터, 다음 「xxxxV.01」 이름(QLSTV.01 등) 전까지
본문
  001c TAG LEN 0000 … LEN 0000 TAG 001f     레코드. 닫는 쪽은 여는 쪽의 거울
                                            보통 i+LEN-4 에 닫힌다. 괘선·그림 자료를 품은 0010 레코드는
                                            LEN 이 앞머리 길이일 뿐이고 훨씬 뒤에 닫힌다 → 거울을 찾아 건너뛴다
  001c TAG LEN … 001d  글자  001e LEN2 … 001f   중첩(칸 이름표 「研究機関名」 등). 안의 글자도 본문이다
  000e                                      홀로 선 표시 워드. 서식(0010) 레코드 앞에 붙는다
  000a                                      줄바꿈
  그 밖                                     글자
본문 뒤               문자 코드표 같은 다른 세그먼트가 붙는다 — 거기까지 걸어가면 어긋난다
레코드 종류(표본)     0030(글자 모양) 0010(문단·괘선) 0000 0001(중첩)
```

**처음 세운 가설 두 개가 틀렸다.** 닫는 쪽을 5워드(0000 LEN 0000 TAG 001f)로 봤는데, 내용이 우연히
0000 으로 끝나는 레코드에서만 맞았다. 그리고 000e 를 멈춤으로 봐서 본문 절반에서 멈췄다.

**글자 수를 바꾸지 않는다.** `DocumentTextPositionTables` · `LineMark` · `PageMark` 가 워드 번호로
줄 위치를 가리킨다. 그래서 **빈칸(공백) 자리에 덮어쓴다** (`jtdFit`):
앞뒤 같은 부분을 떼고, 짧아지면 공백으로 채우고(지운 자리가 전각이면 전각), 길어지면 뒤→앞 공백을 먹는다.
못 맞추면 저장을 거부하고 화면에서 그 줄을 빨갛게 표시한다.

결과: 파일 크기 그대로, 바뀐 바이트 = 고친 글자 × 2, **DocumentText 말고 다른 스트림은 한 바이트도 안 바뀐다.**
네 표본 모두 왕복 통과. 브라우저 끝에서 끝까지(`npm run test:e2e <jtd> ja`)도 통과.

⚠ **아직 사람이 一太郎ビューア 로 열어 본 적이 없다.** 저장본: `Downloads/jtd-samples/*_記入テスト.jtd`.
사진·서명·글자 서식은 一太郎 에서 막아 뒀다(그림·서식 레코드를 아직 모른다).

### 一太郎 (.jtd) — 첫 실측

표본: 문부과학성 과학연구비 신청 양식(様式A) 4개, `Downloads/jtd-samples/`.

- **hwp 와 같은 CFB 통.** 지금의 `readCFB` 가 수정 없이 연다. 쓰기(`writeInPlace`·`cfbAddStream`)도 같은 통이라 재사용할 수 있을 것이다.
- **스트림이 압축돼 있지 않다.** hwp 보다 단순한 부분.
- 스트림: `DocumentText` `Font` `Header` `Footnote` `LineMark` `PageMark` `PaperMark`
  `DocumentEditStyles` `DocumentViewStyles` `DocumentTextPositionTables` `JSRV_*` …
- `DocumentText` 는 **UTF-16BE**(hwp 는 LE). 글자 사이에 제어 레코드가 끼어 있다.
  뽑아 보면 「平成　　年　　月　　日」「代表者職・氏名　　職印」 처럼 **빈칸 있는 양식 글자가 그대로** 나온다.

아직 모르는 것 — 다음에 실측할 것:

1. 제어 레코드의 구조 (줄바꿈·표·칸)
2. 표가 `DocumentText` 안에 있는지 다른 스트림에 있는지
3. 글자 수가 바뀔 때 `DocumentTextPositionTables`·`LineMark` 를 같이 고쳐야 하는지
   — hwp 의 `PARA_LINE_SEG` 자리. 여기가 제일 위험하다
4. 저장본 확인은 **一太郎ビューア**(윈도우 무료)로 사람이 연다

참고: OpenJTD(Rust) 가 텍스트 추출까지 했다. 채워서 **다시 저장**한 사례는 못 찾았다.

## 파일 포맷 — 다시 알아내려면 오래 걸리는 것들

### HWP 5.0

OLE 복합문서(CFB, 옛 `.doc` 과 같은 컨테이너) 안에 zlib(raw deflate) 로 압축된 스트림.

```
FileHeader              256B. 32번지 버전, 36번지 플래그
  플래그 bit0 압축 · bit1 암호 · bit2 배포용 · bit4 DRM
DocInfo                 글자모양·테두리·글꼴 목록 (아직 안 읽음)
BodyText/Section0..N    본문
BinData/BIN000N.png     삽입 이미지 (있을 때만)
PrvText                 미리보기 텍스트. 압축 안 되어 있어서 그냥 읽힌다
```

레코드 헤더 4바이트: **태그 10비트 · 수준 10비트 · 크기 12비트**.
크기가 `0xfff` 면 뒤에 4바이트가 더 온다. 수준이 트리 깊이다.

**PARA_HEADER (24B)** — 오프셋을 실측으로 맞춘 값이다.

```
 0  U32  글자 수.  ★ 최상위 비트는 글자 수가 아니라 별개 플래그다.
                     뜻을 모르므로 하위 31비트만 고치고 그대로 보존한다.
12  U16  글자 모양 수
16  U16  줄 수
```

**LIST_HEADER = 표의 셀 (47B)**

```
 0  I32  이 셀의 문단 수
 8  U16  열 주소     10  U16  행 주소
12  U16  가로 병합   14  U16  세로 병합
16  U32  폭(HWPUNIT) 20  U32  높이
24  U16×4 여백
```

**TABLE**

```
 4  U16 행 수    6  U16 열 수    8  U16 셀 간격
10  U16×4 여백
18  U16×행수  RowSize[] — 각 행의 셀 개수
```

**셀의 문단은 LIST_HEADER 의 자식이 아니라 뒤따르는 형제다.**
LIST_HEADER 가 "내 문단은 N개" 라고 적어 두고 그 수만큼 가져간다.
자식으로 착각하면 표가 통째로 비어 보인다.

**PARA_TEXT** 는 UTF-16LE. 제어문자 `0·10·13` 은 1 WCHAR,
`1~9·11·12·14~23` 은 **8 WCHAR** 를 먹는다. 이걸 틀리면 그 뒤 글자가 전부 밀린다.
문단 끝 줄바꿈(13)이 여기 포함되고 글자 수에도 센다.

**빈 문단에는 PARA_TEXT 레코드가 아예 없다.** 헤더의 글자 수만 1(줄바꿈 하나)이다.
채우려면 PARA_HEADER 바로 뒤에 레코드를 새로 끼워야 한다.

**HWPUNIT = 1/7200 인치.** `PARA_LINE_SEG` 에 줄마다 세로위치·줄높이·베이스라인·
세그먼트 폭이 **이미 계산되어** 들어 있다. 원본처럼 그리려면 이걸 쓰면 되고,
레이아웃을 계산할 필요가 없다.

### HWPX

zip + XML(OWPML). **모델이 HWP 와 같다. 표현만 다르다.**

```
PARA_HEADER  →  <hp:p>
PARA_TEXT    →  <hp:t>
TABLE        →  <hp:tbl rowCnt colCnt>
LIST_HEADER  →  <hp:tc> + <hp:cellAddr> <hp:cellSpan> <hp:cellSz>
PARA_LINE_SEG→  <hp:lineseg>          ← 좌표도 그대로 있다
```

```xml
<hp:p><hp:run charPrIDRef="13">
  <hp:tbl rowCnt colCnt>
    <hp:tr><hp:tc>
      <hp:subList><hp:p><hp:run><hp:t>텍스트</hp:t></hp:run></hp:p></hp:subList>
      <hp:cellAddr colAddr="0" rowAddr="0"/>
      <hp:cellSpan colSpan="1" rowSpan="1"/>
      <hp:cellSz width="52718" height="600"/>
    </hp:tc></hp:tr>
  </hp:tbl>
</hp:run></hp:p>
```

### 그림 — 2026-09-13 실측

`probe-image.mjs` 로 파일 넷을 뜯어 잰 값이다. **짐작 없음.**

그림 하나가 **세 군데에** 나뉘어 들어간다. 하나라도 빠지면 한글이 못 찾거나 안 열린다.

```
BinData/BIN000N.png   통 안의 새 스트림. 이미지 바이트
DocInfo  BIN_DATA     "이런 그림이 있다" 12바이트 + ID_MAPPINGS 개수 올리기
BodyText gso 3층      본문 어디에 얼마나 크게 놓을지
```

**BIN_DATA (12B)**

```
0  U16  속성    0x01 = 스토리지 압축 따름 · 0x21 = 무압축
2  U16  ID      1부터. SHAPE_COMPONENT_PICTURE 가 이 번호를 가리킨다
4  U16  확장자 길이(WCHAR)
6       확장자 UTF-16LE   "png" / "jpg"
```

표본의 png 는 전부 `0x21`(무압축)이라 스트림 앞에 PNG 시그니처가 그대로 보였고,
jpg 하나는 `0x01` 이라 deflate 되어 있었다. **새로 넣을 때는 `0x21` 이 쉽다** — 안 압축하고 그대로 담는다.

`ID_MAPPINGS`(태그 17)는 U32 배열이고 **첫 칸이 BinData 개수**다. 안 올리면 그림을 못 찾는다.

**본문은 3층이고, 그림은 `gso` 의 손자다.** 직계 자식만 보면 못 찾는다 — 실제로 한 번 놓쳤다.

```
CTRL_HEADER 'gso '           개체 공통 — 위치와 크기
└ SHAPE_COMPONENT '$pic'     초기 크기 · 현재 크기 · 변환 행렬
  └ SHAPE_COMPONENT_PICTURE  네 점 · 자르기 · BinItem ID
```

```
CTRL_HEADER 'gso '                 SHAPE_COMPONENT (196B 고정)
 0  U32   ctrl id (뒤집힘)           0  '$pic' ×2 (뒤집힘)
 4  U32   속성                       8  U32 그룹 내 x · 12 y
 8  U32   세로 오프셋               16  U16 그룹 수준 · 18 로컬 버전
12  U32   가로 오프셋               20  U32 초기 폭 · 24 초기 높이   ← 원본 크기
16  U32   폭    (HWPUNIT)           28  U32 현재 폭 · 32 현재 높이   ← 그려지는 크기
20  U32   높이                      36~ 속성 · 회전 · 변환 행렬(double)
24  I32   z-order
28  I16×4 바깥 여백              SHAPE_COMPONENT_PICTURE (91B 고정)
36  U32   instance id              0  U32 테두리 색 · 4 두께 · 8 속성
40  U32                           12  I32×8 네 점 (0,0)(w,0)(w,h)(0,h)
44  U16   설명문 길이(WCHAR)       44  I32×4 자르기 left top right bottom
          + 설명문 + NUL           60  I16×4 안쪽 여백
                                   68  I8 밝기 · 69 I8 대비 · 70 U8 효과
                                   71  U16 BinItem ID   ★
                                   73~ 18B
```

**`71` 은 4바이트 정렬이 안 맞는 자리다.** 앞 필드를 잘못 세면 0 이 나온다.
그림이 둘인 파일(부산대, ID 1·2)로 대조해서 **달라지는 바이트 하나**로 찾았다.

**자르기 단위는 픽셀 × 75** 다. 75 = 7200/96, 96dpi 기준 HWPUNIT.
2585×472 픽셀 그림의 자르기가 `0,0,193860,35400` 이었다.

**품은 문단**은 확장 제어문자 8 WCHAR 를 갖는다. `WIDE` 집합에 이미 들어 있는 코드 11 이다.

```
[0] 11        개체 코드
[1..2] 'gso ' 4바이트
[3..6] 0
[7] 11        같은 코드 반복
              PARA_HEADER 의 글자 수에 이 8 이 포함된다
```

### 통에 스트림을 새로 붙일 여유 — 자사양식.hwp 기준

```
디렉터리 빈 슬롯  3개      필요 2개 (BinData 스토리지 + 그림)        ✓
FAT 빈 칸        164      뒤에 덧붙이기 33 KB + 파일 안 빈 섹터 50 KB  ✓
DIFAT            109칸 중 2 사용. FAT 을 늘려야 할 때도 자리 있다
```

**통을 다시 지을 필요가 없다.** 빈 FAT 칸으로 사슬을 만들고, 빈 디렉터리 슬롯에 항목을
넣고, 모자란 만큼만 파일 뒤에 섹터를 붙인다. 기존 바이트는 안 건드린다 — 지금 방식 그대로다.

다만 **양식 파일에는 BinData 스토리지가 아예 없다.** 스토리지 항목을 새로 만들어
디렉터리 트리에 끼워야 하고, 이게 이 작업에서 제일 조심할 곳이다.
부산대 파일은 반대로 스토리지는 있는데 **빈 슬롯이 0개**라 디렉터리 섹터를 늘려야 한다.

**DocInfo 와 BodyText 는 새 코드가 필요 없을 수 있다.** 둘 다 지금의
「제자리 덮어쓰기 + 크기 예산」으로 처리된다. DocInfo 는 16바이트, BodyText 는
500바이트쯤 늘어나는데 자사양식의 여유가 2,500바이트였다.
**새 통 작업이 필요한 건 이미지 바이트뿐이다.**

### 실제 파일 표본 (다운로드 폴더의 채용 문서 8개)

```
전부 flags=0x0001 (압축만). 암호·DRM·배포용 0건
전부 레코드가 스트림 길이와 정확히 일치. 미지 태그 0개
양식은 빈칸이 69~191개, 공고문은 2~7개  ← 이 분포가 파싱이 맞다는 증거다
```

## 그림 넣기 — 2026-09-13

상태: **표본 8개 구조 검증 통과. 화면에서도 넣을 수 있다. 한글로 열어본 사람이 아직 없다.**

화면에서 쓰는 법: 위 「사진 넣기」 → 파일 고르기 → **넣을 칸을 클릭**.
칸 안에서 슬라이더로 크기를 줄이고, 「빼기」 로 되돌린다. Esc 로 고르기를 취소한다.

칸마다 버튼을 두지 않은 이유는 표가 버튼밭이 되기 때문이다. 그리고 어느 칸에나
넣을 수 있어야 한다 — 사진 칸을 파일에서 알아맞히는 방법이 없다.

**사진을 넣은 문단은 글자 수정 대상에서 뺀다.** 같은 문단에 둘 다 하면
글자 갈아치우기가 그림을 가리키는 제어문자를 지워 버린다.

바이트는 **저장할 때** 만든다(기본 300dpi). 슬라이더마다 다시 인코딩하면 손이 느려지는데
어차피 쓰이는 건 마지막 값 하나다. 용량이 4096B 미만이면 품질을 올리고,
그래도 모자라면 화소를 키운다 — **물리 크기는 안 건드린다.**

```bash
node test-image.mjs "<그림 든 hwp>" "<대상 hwp...>"
```

넣을 그림은 **다른 hwp 에서 꺼낸 진짜 PNG** 를 쓴다. 만들어 낸 바이트로 하면
통과해도 실제 그림에서 되는지 모른다.

### 통을 다시 짓지 않는다

`cfbAddStream()` 이 하는 일은 **빈 자리를 찾아 쓰는 것**뿐이다.
BodyText 를 제자리에 덮어쓰는 것과 같은 원칙이다.

```
빈 FAT 칸을 찾아 사슬을 만든다
빈 디렉터리 슬롯에 항목을 넣는다
모자란 만큼만 파일 뒤에 섹터를 붙인다
```

자사양식(98 KB)에 32 KB 짜리 PNG 를 넣었더니 **파일 크기가 그대로였다.**
파일 안에 안 쓰는 섹터가 50 KB 있었기 때문이다.

색인이 꽉 찬 파일도 있어서 늘리는 길을 둘 다 만들었다. 표본에서 실제로 둘 다 걸렸다.

```
FAT 이 꽉 참        새 FAT 섹터가 자기가 여는 구간의 첫 번호를 자기 자리로 쓴다
                    (안 그러면 닭과 달걀이 된다) + DIFAT 109칸에 등록
디렉터리가 꽉 참     디렉터리 사슬에 섹터를 하나 잇는다
```

**파일 안의 빈 섹터를 재활용할 때는 반드시 지우고 쓴다.** 예전 쓰레기가 남아 있다.

### 제일 위험한 곳

**디렉터리 트리를 평범한 이진 탐색 트리로만 끼운다.** 원래는 레드-블랙 트리고
색까지 맞춰야 하는데, 새 항목을 그냥 검정으로 둔다. 읽는 쪽이 색을 거의 안 보기 때문에
동작할 것으로 보지만, **이게 틀리면 한글이 파일을 아예 못 연다.**
이름 비교 순서는 맞췄다 — **길이가 먼저**, 그 다음 대문자 비교 (MS-CFB 2.6.4).

두 번째로 위험한 곳은 `CTRL_HEADER` 의 속성값이다. 표본이 전부 **떠 있는 그림**이라
칸 안에 넣는 값의 실측이 없다. 표본값(`0x040a6000`)에 「글자처럼 취급」 비트를 켠
`0x040a6001` 을 쓴다. 이건 짐작이다 — 그림이 엉뚱한 데 놓이면 여기부터 본다.

### 못 하는 것

```
PIC_TOO_SMALL     4096B 미만은 미니 스트림에 들어가야 하는데 그 경로는 안 만들었다
NEED_DIFAT_SECTOR DIFAT 109칸이 다 찬 아주 큰 파일. 표본은 2~5칸 썼다
```

### DocInfo 와 BodyText 는 새 코드가 없었다

둘 다 지금의 「제자리 덮어쓰기 + 크기 예산」 그대로 처리된다.
DocInfo 는 16바이트, BodyText 는 340바이트쯤 늘어나는데 여유가 2,500바이트였다.
**통 작업이 필요한 건 이미지 바이트뿐이었다.**

글자 고치기와 그림 끼우기는 **한 줄에 세워 뒤에서 앞으로** 처리한다.
둘 다 레코드를 끼우기 때문에, 따로 돌리면 뒤쪽 작업이 엉뚱한 레코드를 잡는다.

## 글자 크기 · 줄간격 — 2026-09-13 실측

상태: **왕복 검증 통과. 한글로 열어본 사람이 아직 없다.**

크기와 줄간격은 본문이 아니라 **DocInfo** 에 있다. 고치려면 거기에 레코드를 새로 만들고
`ID_MAPPINGS` 개수를 올린 다음, 문단이 그 번호를 가리키게 한다.
**BIN_DATA 와 완전히 같은 방식**이라 새로 판단할 게 거의 없었다.

```
CHAR_SHAPE  74B   42번지 INT32 = 기준 크기, 1/100 pt   (1100 = 11pt)
PARA_SHAPE  58B   24번지·50번지 INT32 = 줄간격 %        (150 = 150%)
                  0번지 속성1 의 하위 2비트가 0 이어야 % 로 읽는다
```

**24번지와 50번지에 같은 값이 들어 있다.** 구버전·신버전 자리인데 표본이 둘 다 채워
두고 있어서 우리도 둘 다 쓴다. 하나만 쓰면 어느 한글에서 무시될 수 있다.

**번호는 등장 순서다.** 그래서 새 레코드를 같은 태그의 **맨 뒤**에 붙이고,
새 번호 = 원래 개수(0부터 센다)로 잡는다. BinData 만 1부터 센다.

`ID_MAPPINGS` 칸 번호도 실측이다. 각 칸의 값이 레코드 수와 정확히 맞는 걸로 확인했다.

```
[0] BinData   [1..7] 글꼴 7종   [8] BORDER_FILL   [9] CHAR_SHAPE
[10] TAB_DEF  [11] NUMBERING   [12] BULLET       [13] PARA_SHAPE   [14] STYLE
```

문단이 쓰는 번호는 `PARA_HEADER` 8번지(U16)가 문단 모양, `PARA_CHAR_SHAPE` 의
(위치, 번호) 쌍이 글자 모양이다. **글자 모양은 줄 전체를 하나로 통일한다** —
줄 안에서 일부만 바꾸는 건 안 만들었다.

**글꼴 종류는 아직이다.** 한글·영문·한자로 목록이 7개 갈려 있고 FACE_NAME 을
같이 만들어야 해서 크기보다 한 단계 번거롭다.

## 자필 서명

**투명 PNG 로 굽는다.** JPEG 으로 구우면 배경이 흰 네모가 되어 서명란 위에
종이를 덧댄 꼴이 된다. 그린 부분만 알파값으로 찾아 잘라 낸다 —
빈 여백까지 넣으면 칸 안에서 서명이 작아진다.

**서명 PNG 는 대개 4096B 아래다.** 선 몇 개라 그만큼 잘 압축된다.
그런데 통에 스트림으로 넣으려면 4096B 이상이어야 한다(미니 스트림 경로가 없다).
`padPng()` 가 `tEXt` 주석 청크를 IEND 앞에 끼워 크기를 맞춘다. 표준 보조 청크라
어느 뷰어든 그냥 건너뛰고, **그림 자체는 한 픽셀도 안 변한다.**

서명은 표 밖 줄에 들어가는 일이 많다(「성명    (서명 또는 날인)」).
그래서 그림 넣기가 **클릭한 글자 자리**를 받는다. 제어문자 8 WCHAR 를 그 위치에
끼우고 글자 모양 목록의 그 뒤 항목들을 8 만큼 민다.

### 글 앞으로 띄우기 — 2026-09-14

「글자처럼 취급」 으로 끼우면 서명이 `(서명)` **옆에** 들어가 글자를 밀어낸다.
표 밖의 글자 있는 줄에 놓은 그림은 이제 **글 앞으로** 뜬다 (`PIC_ATTR_FRONT = 0x046a6210`).

```
개체 공통 속성 (CTRL_HEADER 4번지)
bit 0      글자처럼 취급      0
bit 3-4    세로 기준          2 문단        ← 오프셋은 8번지, 문단 위 기준. 음수 됨
bit 8-9    가로 기준          2 단          ← 오프셋은 12번지, 단 왼쪽 기준
bit 14     겹침 허용          1
bit 18-19  높이 기준          (표본값 그대로)
bit 21-23  본문과의 배치       0 어울림 · 1 자리 차지 · 2 글 뒤로 · 3 글 앞으로
```

**배치는 21-23번이다.** `probe-anchor.mjs` 둘째 판은 18-20번을 돌려서 후보가 전부
「어울림」 이었다 — 그 시험 파일로는 아무것도 알 수 없었다. 지금 값은 규격에서 짰고,
**뷰어로 열어 확인한 사람은 아직 없다** (`Downloads/..._서명시험.hwp`).

**뜨는 건 확인됨 (2026-09-14, 웨일 뷰어).** 글자를 밀지 않고 겹쳤다. 그런데 화면에서
`(서명)` 위에 놓은 서명이 파일에서는 **이름 위에** 떨어졌다. 그 줄이 **오른쪽 정렬**인데
화면은 전부 왼쪽 정렬로 그리고, 왼쪽에서 잰 px 를 그대로 옮겼기 때문이다.

그래서 이제는 두 가지를 한다.

```
화면   PARA_SHAPE 속성1 2-4번 비트로 정렬을 읽어 text-align 에 입힌다
저장   정렬이 붙는 쪽 끝에서 잰다   floatOffX()
         오른쪽  줄 끝(PARA_LINE_SEG 24+28번지) − 오른쪽 끝까지 남은 px
         가운데  줄 가운데 + 가운데에서 떨어진 px
         나머지  줄 시작 + 왼쪽에서 떨어진 px
```

화면과 한글은 글꼴 폭·줄 폭이 다르다. 붙는 쪽 끝에서 가까운 글자일수록 양쪽이 같아서
「(서명)」 은 거의 안 어긋난다. 반대쪽 끝에 놓으면 여전히 몇 mm 틀릴 수 있다.

떠 있는 그림은 **글자 고치기와 같은 문단에 같이 된다.** 글자를 먼저 통째로 갈고
제어문자를 맨 뒤(줄바꿈 앞)에 붙이므로 서로를 안 지운다. 「지원자 :이정준」 을 쓰고
서명을 올리는 게 한 번에 저장된다. 글자처럼 취급하는 그림은 여전히 막는다.

## 설계 — 왜 이렇게 했나

```
1  CFB/zip 열기   스트림 + 각 스트림이 어느 섹터/어느 바이트에 있는지 기억
2  압축 해제
3  레코드/XML 파싱  ★ 원본을 통째로 보관한다
4  문서 모델       문단·표·셀. 3을 가리키는 참조만 들고 있다
5  화면            읽기 전용 투영. HTML 이든 canvas 든 무관
6  저장            4의 참조로 3을 고침 → 직렬화 → 압축 → 원래 자리에 덮어씀
```

**핵심은 3번이다.** 원본이 그대로 남아 있어서 **우리가 안 건드린 것은 바이트가 안 변한다.**
뜻을 모르는 레코드도 안전하게 통과한다.

**컨테이너를 다시 짓지 않는다.** hwp 는 BodyText 가 들어 있던 그 섹터에 덮어쓰고,
hwpx 는 고친 항목만 다시 압축해 zip 을 다시 묶는다(로컬 헤더·중앙 디렉터리 바이트는 보존).
CFB 를 새로 짜면 FAT·miniFAT·디렉터리·DIFAT 을 전부 다시 배치해야 하는데,
한 군데만 틀려도 한글이 파일을 아예 못 연다.

**크기 예산 (hwp 만).** 원래 자리에 덮어쓰므로 **새 압축본이 원본 스트림 크기를 넘으면
저장이 거부된다**(`TOO_BIG`). 실제로는 거의 안 걸린다 — 브라우저 압축기가 원본을 만든
것보다 잘 줄인다(자사양식 7507B → 5000B 남짓). 94곳을 다 채워도 들어갔다.
이걸 넘겨야 하는 날이 오면 그때가 **CFB 라이터가 필요한 날**이다 (= 이미지·서명).

**표시와 저장은 완전히 별개다.** canvas 는 픽셀이라 hwp 로 되돌아갈 수 없다.
저장은 항상 레코드를 고쳐서 한다. 화면을 어떻게 그리든 6번은 안 바뀐다.

**서버를 두지 않는다.** 읽기는 이미 완벽하다 — 서버가 개선하는 건 렌더링 품질이고
그것도 한컴 렌더러를 빌리는 것뿐이다. 이력서가 서버를 거치는 순간 이 도구의 존재 이유가
사라지고, 더 못한 한컴독스가 된다.

## 겪은 사고들

전부 **화면에는 아무 표시가 없어서** 눈으로는 못 잡는 것들이다.

- **레코드의 `data` 는 원본 스트림을 가리키는 뷰다.** 거기 직접 쓰면 화면이 들고 있는
  문서 모델까지 같이 바뀐다. 글자 수처럼 **더하고 빼는 값**은 그래서 저장을 두 번
  누르면 두 번 더해졌다. 첫 파일은 멀쩡하고 **두 번째부터** 글자 수가 실제와 어긋나는데,
  우리 파서는 그 값을 안 보므로 다 통과하고 **웨일 뷰어만 「문서를 불러오지 못했습니다」** 를 띄웠다.
  사람은 저장을 두 번 누른다. `ownHeader()` 로 머리를 사본으로 바꿔 쓰고,
  `test-twice.mjs` 가 세 번 저장해 바이트가 같은지 본다.
- **개체 식별 번호를 시계로 만들면 안 된다.** 저장할 때마다 파일이 달라져서
  「두 번 저장하면 같은가」 를 검사할 수 없다. 값에서 만든다.
- **화면에 안 비치는 기능은 없는 기능이다.** 글자 크기는 파일에 제대로 들어가고 있었는데
  화면이 그대로라 되는지 알 수가 없었다. 지금은 원래 크기도 화면에 반영하고,
  적용하면 그 자리에서 바뀐다.
- **`DecompressionStream` 은 `inflateRawSync` 보다 엄격하다.** CFB 스트림은 패딩되어
  있어서 deflate 가 끝난 뒤에도 바이트가 남는데, Node 는 무시하지만 브라우저는
  "Trailing junk" 로 던진다. 청크로 모으다가 끝의 그 오류만 넘긴다.
  **잡히지 않은 거부가 읽기·쓰기 양쪽으로 퍼지므로 세 군데를 다 받아 둬야 한다.**
- **글자 모양(`PARA_CHAR_SHAPE`)은 "몇 번째 글자부터 어떤 서식" 목록이다.**
  글자 수가 줄면 뒤쪽 항목이 없는 위치를 가리킨다. 빈 칸은 모양이 1개라 이 경로가
  없어서, **「‘ . . ~ ’ . . ( 년 월)」 같은 틀을 열어주는 순간 처음 밟는 코드**였다.
- **자기닫힘 `<hp:t/>` 에는 내용을 못 넣는다.** 그 자리에 끼우면 `<hp:t/>홍길동` 이 되어
  글자가 태그 밖으로 나간다. 태그째 펴야 한다.
- **표를 품은 문단은 고치면 안 된다.** 그 문단의 글자에는 표를 가리키는 참조가 들어
  있어서, 통째로 갈아치우면 **표가 떨어져 나간다.** 양쪽 저장 경로에서 막았고
  화면에서는 입력칸 대신 그 표를 그린다. hwpx 를 붙이다 발견했는데 **hwp 에도 있던 구멍**이다.
- **`□` 는 도형이 아니라 글자(U+25A1)다.** 체크는 `■`(U+25A0) 로 바꾸면 끝이라
  파일 구조를 건드릴 일이 없다. `▣`(U+25A3)는 머리표이지 체크칸이 아니므로 제외한다.
- **빈 칸만 입력칸으로 만들면 안 된다.** 글자가 있다는 이유로 「채우라고 넣어 둔 틀」이
  라벨로 분류된다. 파일만 봐서는 라벨과 틀을 구분할 방법이 없으니 **구분하려 들지 말고**
  전부 열어 두되 원래 비어 있던 칸만 강조한다.
- **`file://` 더블클릭에서는 ES 모듈이 CORS 로 막힌다.** 그래서 한 파일에 담았다.

## prelaps 도구로 올릴 때

**심사 중에는 배포하지 않는다.** 이 폴더에는 `wrangler.jsonc` 도 `package.json` 도 없어서
올릴 수가 없다 — 의도한 것이다. `TODO-adsense.md` 가 심사 중 페이지 증가를 막고 있다.

> **[2026-09-15 갱신]** 애드센스가 불합격으로 끝나 심사 중 동결은 풀렸다. 만들어서 배포·색인까지 간다.
> 주소 순서도 바꿨다 — 헌법이 「언어판은 `/<도구>/<언어>/` 아래」 라서 **언어 다음에 형식**이다.
> 형식은 한 페이지 안의 탭이고, 탭마다 아래 주소를 갖는다. PDF 는 뺐다(경쟁이 너무 많다).
>
> ```
> prelaps.com/form/            언어 고르는 통로 (Accept-Language 302)
> prelaps.com/form/ko/         = /form/ko/hwp/ 가 기본 탭
> prelaps.com/form/ko/hwp/
> prelaps.com/form/ja/jtd/     一太郎 가 일본어 기본 탭
> ```
>
> 아래는 예전 계획(형식 다음 언어)이라 참고만 한다.

승인 후 구조는 이렇게 이야기가 됐다. 포맷마다 URL 은 다르되 **폴더 하나 · 배포 하나**:

```
prelaps.com/form/            포맷 고르는 통로
prelaps.com/form/hwp/ko/     site/hwp/ko/index.html
prelaps.com/form/hwpx/ko/
prelaps.com/form/docx/ko/

routes = [ "prelaps.com/form", "prelaps.com/form/*" ]   ← 처음이자 마지막. 포맷 늘어도 안 건드림
```

라우터 `TOOLS` 도 허브 `tools.ts`·`robots.txt` 도 **처음 한 번만** 손대면 된다.
사이트맵이 도구 안에 있어서 포맷 추가는 같은 배포에 딸려 간다.
URL 이 파일 경로와 한 칸 차이라 **접두사 제거 사고(`/styles.css` → `"ss"`)가 날 자리가 없다.**

언어별 주력이 다르다 — `hwp` 는 ko, `xlsx` 는 ja(엑셀 모눈종이 양식), `pdf` 는 en.
각 포맷이 세 언어를 다 갖추므로 hreflang 은 그대로 맞는다.

나머지는 `prelaps-tool-template/README.md` 와 헌법(§7 도구 추가 체크리스트)을 따른다.
